# STRIDE Threat Model - Cryptographic Audit Ledger

| Threat Category | Description | Specific Impact on NetSentinel | Mitigation |
|---|---|---|---|
| **Spoofing** | Forging audit entries to create a false trail of legitimate activity. | False evidence of authorized testing; framing an innocent party. | Hash chain (`SHA-256(prev_hash || content)`) makes forgery computationally infeasible — each entry depends on all prior entries. Verification via `AuditLedger::verify_integrity()` walks the full chain recomputing hashes. First corrupt entry is identified and reported. |
| **Tampering** | Modifying or deleting past audit entries to hide evidence of unauthorized activity. | Destruction of evidence; compliance failures; legal exposure. | Append-only design — no `UPDATE` or `DELETE` operations on the ledger table. SQLite WAL mode with file permissions `0600` (owner-only). HMAC-SHA256 signed JSONL backup (`/var/log/netsentinel_audit.jsonl`) provides independent verification channel. Integrity check runs at application startup with `Adw.Banner` warning if chain is broken. |
| **Repudiation** | Operator claims audit entries were fabricated or tampered with. | Dispute over authenticity of logged actions. | Chain verification is deterministic and reproducible — any party can independently verify. Optional GPG-detached signature on ledger exports for third-party auditor verification. Consent hash (RE-01) is embedded in the chain, linking each session to a cryptographic proof of authorization. |
| **Information Disclosure** | Unauthorized access to the audit ledger database containing session history, targets, and operator identities. | Exposure of client engagement details, test targets, and vulnerability findings. | SQLite file encrypted via SQLCipher (AES-256) with key derived from GNOME Keyring. File permissions `0600` on the database. D-Bus access to ledger restricted to UI daemon process only. No ledger data transmitted over network — local storage only. |
| **Denial of Service** | Filling the audit ledger with garbage entries to exhaust disk space or slow down integrity verification. | Application becomes slow; integrity checks take excessive time; disk exhaustion. | Configurable retention policy (default 30 days) with automatic purge via `systemd timer`. Ledger entries are fixed-size JSONL — predictable storage growth. `verify_integrity()` can be run in a background thread with progress reporting. Maximum entry count configurable as a safety limit. |
| **Elevation of Privilege** | Exploiting a vulnerability in the SQLite/WAL engine or the SHA-256 computation to gain code execution. | Arbitrary code execution in the context of the ledger process. | SQLite is a well-audited, mature library. WAL mode limits the attack surface. No user-controlled data is interpolated into SQL queries — all inserts use parameterized statements. SHA-256 computation uses the `sha2` crate (pure Rust, no `unsafe`). No custom cryptography — standard library primitives only. |
